## 3. Refusal behaviour

**Root cause of the baseline failures.** Retrieval relevance was treated as evidence. Near-miss questions retrieve same-service incidents about different problems, and their scores overlap real matches: out-of-scope top scores reach up to 0.82, while relevant incidents go as low as 0.65. No threshold can separate them.

**Fix: an evidence match check, enforced in code.** A new LangGraph node, `incident_matching` (`agents/incident_matcher.py`, gpt-4.1-mini at temperature 0), classifies each retrieved incident as `same_problem`, `related_not_same` or `unrelated`. The prompt states explicitly that plausible causation is not a match. Application code then:
- uses only `same_problem` incidents as evidence;
- joins deployments, logs and the runbook only to those incidents;
- when none match, returns a deterministic evidence-policy answer with no LLM call: "The available incident records do not establish the cause…", listing the related records reviewed and the data needed. It never offers hypotheses drawn from non-matching incidents.

There is no special-casing of phrasing or questions: "what might cause…" questions are answered whenever a record describes the asked problem.

**Validation before integration** (`python -m evals.evaluate_matcher`, temperature 0):

| Set | in-scope full recall | precision | multi full recall | OOS with nothing matched |
|---|---|---|---|---|
| testset_v1, 75 Qs not inspected (dev + held-out) | 0.984 | 0.976 | 0.875 | 0.846 (11/13) |
| **fresh, never-seen calibration set** (`matcher_calibration_v1.jsonl`, 36 Qs) | **1.000** | 1.000 | — | **0.938** (15/16) |

**Disclosure.** The match prompt was revised once after seeing test-set misses, to state the general rule that "plausible causation is not a match". One further clause was tried and then reverted after measurement. The fresh set was generated after that revision, to check generalisation.

**Second check, tried and reverted.** I also tried having the generator re-confirm the match. On the fresh set it changed nothing; on the inspected failures it fixed 0 of 3 out-of-scope cases and created 1 new false refusal. It was removed.

## 4. Grounding and faithfulness

**Changes:**
- **Structured output.** The model returns JSON separating confirmed facts, evidence-backed conclusions, labelled hypotheses, limitations, unknowns and advice. Every claim must cite record IDs (`agents/rca_structured.py`).
- **Deterministic post-generation checks.** These remove any claim that:
  - has no valid citation;
  - names an ID or date that is not in the evidence;
  - presents a root cause that doesn't cite a matched incident.

  Confidence is capped at the computed evidence strength. All removals are recorded in `grounding_issues`: 0.22 per answer on average, visible in the trace metadata.
- **Evidence strength separated from retrieval relevance.** Strength is computed per matched incident:
  - HIGH requires its own verified deployment, plus corroborating time-aligned logs, plus a strong match;
  - a contradiction, such as a quarantined link, forces LOW;
  - for multi-incident answers, the weakest incident sets the strength.

  With the current data no incident can reach HIGH; final strengths are MEDIUM or LOW.
- **Answer shape.** The summary states the answer directly. Caveats are moved into "Unknowns and Missing Evidence" rather than dropped. The root cause is the recorded cause, qualified by the application's evidence notes.

**The 10 worst faithfulness answers (final)** are judge-dominated. Their rejected claims are mostly verbatim restatements of the record, such as "Incident INC-013 records the failure of profile updates to save…" at 0.46 (`88e089bb…`). The **genuine** unsupported claims follow one pattern: **unstated temporal or causal links between a deployment and the incident**. Examples:
- "the deployment coincided with the backend service timeout" (`a90014a3…`, `5b7a5836…`);
- "indicating a temporal and causal relationship" (`88e089bb…`, `b7065370…`);
- "likely related to authentication changes" (`8624d5d9…`).

Other worst cases: `4b3bf39d…`, `0c713c2a…`, `6d9e4dec…`, `b7b9dbb9…`, `866b2ae8…`.

## 5. Judge validation (claim level)

**Sample.** 60 faithfulness claims from the final run (`evals/calibration/claim_labels.csv`):
- 30 judged supported and 30 judged unsupported, oversampling rejections from a pool of 788 / 134;
- the exact evidence the judge saw is inline;
- the `assistant_label` column holds **provisional labels written by Claude Code from the same evidence, not human labels**; the `human_label` column is empty.

**Agreement with the provisional labels** (`python -m evals.claim_calibration agreement --labels assistant`, 55 determinate, 5 indeterminate):

| | Value | 95% CI |
|---|---|---|
| accuracy | 0.69 | 0.56–0.80 |
| Cohen's κ | 0.34 | — |
| judge false-negative rate | **0.36** | 0.24–0.51 |
| judge false-positive rate | 0.00 | 0.00–0.32, only 8 unsupported claims |

Of the 25 determinate claims the judge rejected, 17 restate the records. If these labels hold, the reported faithfulness **underestimates** groundedness. A rough reweighting suggests about 0.95 at claim level.

**Judge-fix experiment** (`python -m evals.judge_batch_experiment`). Each item's full production statement list was re-verified with the same evidence and sibling statements; only the NLI batch size changed. Results against the provisional labels:

| batch size | accuracy | false-negative rate | false-positive rate (n=8) |
|---|---|---|---|
| production (8) | 0.691 | 0.362 | 0.000 |
| 8 (re-run) | 0.691 | 0.362 | 0.000 |
| 4 | 0.709 | 0.319 | 0.125 |
| 1 | 0.764 | 0.213 | 0.375 |

- The batch-8 re-run reproduces production exactly.
- Batch size is a real trade-off: smaller batches mark more supported claims as supported, but also accept more unsupported ones.
- Accuracy differences sit within overlapping CIs, and the false-positive rate rests on only 8 claims, so no change was adopted.
- **Faithfulness is sensitive to this setting.** Smaller batches would raise the score, and the current pass margin is 0.016. Treat the faithfulness pass as setting-dependent until human labels exist.
- An earlier version of this experiment batched only the sampled claims, not production batching. Its "run-to-run variance" conclusion was wrong and has been withdrawn.

**The judge is NOT calibrated.** Calibration requires human labels in `claim_labels.csv` (`--labels human`) and in `calibration_samples.csv`, which has 100 rows from the final run; the earlier exports are kept with run-specific names.
